Avalonia Style Precedence

When more than one thing sets the same property, Avalonia picks a winner by priority. The lowest number wins.

The ladder

From Avalonia.Data.BindingPriority. Same property shown six ways — whichever is present with the lowest number is what renders.

The two everyday cases: a plain style (3) sets the baseline look, and a :pseudo-class style (1) overrides it for a state like :pointerover. A style can also override a Template (2) value — that's how a templated control gets a look from its template that a state then changes. But notice LocalValue (0) beats every style: anything set inline on the element wins over all of them.

The gotcha that catches everyone

These two lines look almost identical. Both set BorderThickness; both contain {TemplateBinding BorderThickness}. One can be overridden by a style — one can’t.

2Template — overridable
BorderThickness="{TemplateBinding BorderThickness}"
The value assigned to the property is a TemplateBinding → priority 2. A :pseudo style (1) can override it.
0LocalValue — not overridable
BorderThickness="{SomeExtension Value={TemplateBinding BorderThickness}}"
The value assigned is whatever {SomeExtension} builds (a Binding/MultiBinding) → priority 0. No style can beat it.
The rule that explains it: priority comes from the outermost binding actually assigned to the property — not from whatever is nested inside it. A {TemplateBinding} wrapped inside another markup extension (a {Binding}, a {MultiBinding}, or any custom one) is no longer “a TemplateBinding” to the property — it is just a data source feeding the outer binding. The property receives the outer binding, and a plain Binding/MultiBinding set inline is LocalValue (0). Only a {TemplateBinding} assigned directly is Template (2).

What that looks like in practice

A control template sets a value inline, and a pseudo-class style tries to change it for one state. If the inline value is a wrapped binding (LocalValue 0), the state override silently does nothing.

✗ Inline binding (0) vs a pseudo-class style (1) — the style is ignored

<!-- in the template: a custom extension wrapping a TemplateBinding -->
<RepeatButton BorderThickness="{SomeExtension Value={TemplateBinding BorderThickness}}"/>   // 0 WINS
<Style Selector="^:left /template/ RepeatButton"><Setter Property="BorderThickness" Value="0"/></Style>   // 1 LOSES

Tell-tale sign: the override has no effect and even a literal "0" in it is ignored → the property is pinned by an inline LocalValue.

✓ Drive both states from styles — now it’s style-vs-style

<!-- no inline value on the element; the default is a plain style (3) -->
<Style Selector="^ /template/ RepeatButton"><Setter Property="BorderThickness" Value="{SomeExtension Value={TemplateBinding BorderThickness}}"/></Style>   // 3
<Style Selector="^:left /template/ RepeatButton"><Setter Property="BorderThickness" Value="0"/></Style>   // 1 WINS

Neither value is a LocalValue now. The default sits at Style (3); the :left trigger at StyleTrigger (1) wins when active.

Rules of thumb

  • Priority = the outermost binding assigned to the property. A nested {TemplateBinding} doesn’t count — it’s only a source.
  • Only a {TemplateBinding} assigned directly is Template (2). Wrap it in anything and the property gets a LocalValue (0).
  • If a state must be able to override a value, set that value from a style — not as an inline binding on the element.
  • Override does nothing and a literal in it is ignored too → you’re fighting an inline LocalValue.
  • Selector specificity can’t help — the priority band is decided first; a more specific StyleTrigger still loses to a LocalValue.
  • Writing a markup extension meant for templates? Set multi.Priority = BindingPriority.Template so it behaves like a real {TemplateBinding} when used inline.
