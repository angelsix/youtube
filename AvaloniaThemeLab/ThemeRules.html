Theme rules

Purpose & Overview

Read ThemePhilosophy.html first: it says why these rules exist and what they protect, which is how to decide a case no rule covers.

File paths in these rules (Controls/Button.axaml, Theme/DefaultTheme.cs) are relative to Themes/AngelSix.Themes.Default.

Avalonia's stock control themes grew organically over years, accumulating legacy patterns, duplicated resources, hard-coded values, and inconsistent styling approaches. The result is a system where restyling even a single control often requires digging through multiple layers of templates, resources, and base themes — and where a global design change (e.g. switching from light to dark, or updating the border radius across all controls) means touching dozens of files individually.

The Token System

This Default theme replaces that with a token-based architecture. A single DefaultTheme.cs class defines every design decision — colors, spacing, type scale, corner radii, control heights, thicknesses — as named tokens. These tokens are exposed as markup extensions in three namespaces, chosen by the C# type of the property they wrap: paint types (Color, anything implementing IBrush) become {color:...} ({color:AccentBrush Light10}), numeric and geometric types (double, Thickness, CornerRadius, ...) become {size:...} ({size:SpacingMd}, {size:RadiusSm}), and everything else stays {theme:...} ({theme:FontFamily}, {theme:StandardAlignmentHorizontal}). Any control theme can reference all three. Every themed file declares the three prefixes on its root element, the two newer ones sitting beside the original theme declaration:

<ResourceDictionary xmlns="https://github.com/avaloniaui"
                    xmlns:theme="using:AngelSix.ThemeEngine.Generated"
                    xmlns:color="using:AngelSix.ThemeEngine.Colors"
                    xmlns:size="using:AngelSix.ThemeEngine.Sizes">
Spelling is American, everywhere.The paint namespace is AngelSix.ThemeEngine.Colors, the prefix is {color:...}, and the ramp attribute is [ColorRamp] — never Colours / colour / [ColourRamp]. The British forms do not resolve; and beyond compiling, the rest of the ecosystem (Avalonia's own Color type, the generated member names, every downstream theme) spells it color, so mixing in a colour reads as a mistake even where it happens to work. When you write a new themed file, declare the namespaces with the themexml snippet: type it on the root element and press Tab.

The effect is transformative:

  • Clean, concise XAML syntax. Instead of referencing resources through string-based keys ({StaticResource MyColor}) with no compile-time checking, you write {color:AccentBrush Light10}, {size:SpacingMd}, {size:RadiusSm}. This is valid XAML that the AngelSix.ThemeEngine source generator understands directly.
  • Full IntelliSense. Because the theme tokens are generated by a Roslyn source generator from the [Theme]-attributed class, your IDE knows every token exists. No more memorising resource key strings or wondering if a key is misspelled — the tokens appear in autocomplete as you type.
  • Instant compilation feedback. A mistyped or removed token becomes a compile error, not a silent runtime fallback to a default value. This catches breaking changes the moment you rebuild, not when you run the app and notice something looks wrong.
  • A theme is a single C# class. To create a dark variant, you subclass DefaultTheme and override the hue you want to change (e.g. AccentNeutral). That's it — every control in the library picks up the new values automatically.
  • No more hunting through XAML for hard-coded colors. Every visual value flows from a named token with a clear purpose.
  • Design consistency is enforced by the type system. You can't accidentally use slightly-different greys in two controls because there's only one Dark3 stage per hue.
  • Consumer apps can further customise by subclassing DefaultTheme themselves, or by setting individual properties on controls through normal styling — because every property is exposed as a theme-backed setter (Rule 1) and uses TemplateBinding inside templates (Rule 2) so consumer styles have proper precedence.

Why Rules?

A token system only works if every control plays by the same rules. If one control hard-codes a color in its template, it silently bypasses the theme and breaks the promise that "changing the theme restyles everything." If another control uses {theme:...} inside a ControlTemplate instead of TemplateBinding, consumers can no longer override that value through normal styles because of Avalonia's style precedence.

These rules exist to codify the architecture so that every control file is predictable, consistent, and themable — and so that new contributors can produce correct control themes without needing to understand every nuance of Avalonia's styling system.

Hard-Coded Values — What Is and Isn't Allowed

StatementEvery color, font family, font size, and font weight on a UI surface flows from a theme token. Hard-coded values are not the default — they are restricted to a small, closed list of exemptions. When you encounter a hard-coded color or font value, replace it with the most suitable theme token. Do not preserve the exact pixel value; pick the token that matches the control's visual role.

BaseSize is a zoom: at BaseSize 2 in a window twice the size every element must land at exactly twice its bounds, and one pixel line (ColumnDefinitions="64,64,64,8", "*,32", MinWidth="160") keeps its size and moves everything after and inside it. Colors: hues and stages

Every color is a hue with a ramp: the hue itself, plus ten evenly-spaced stages either side, the outermost at 97% so no two hues end on the same color. Light1..10 recede towards the canvas and Dark1..10 advance towards the ink. In the light palette that is white and black. In the dark palette the Light stages travel towards the canvas (the Surface hue's DarkSeed, #222222), keeping the colorfulness of their light twin, and the Dark stages travel towards white.

Stage N is one lightness in every hue. Neutral and the eight chromatic hues carry [ColorRamp(HueAware = true)]: each stage sits at a fixed OKLCH lightness, stepping from L 0.60 towards white, black or the canvas, and the seed gives only hue and chroma (chroma is reduced where sRGB cannot show it). So Dark3 is 5.19-8.16:1 on the light canvas and 6.0-6.6:1 on the dark one whatever Accent.Kind says, and a role pinned to a stage means the same thing in every hue. The light palette's hued ink stages (Dark3-Dark7 for the eight chromatic hues) are declared in DefaultTheme.cs: each keeps its OKLCH hue, gains a little lightness (+0.03 at Dark3 tapering to +0.005 at Dark7) and takes full gamut chroma, so light-theme accents read vibrant instead of near-black. Solid (checked, filled, selected) faces use four roles pinned to real ramp stages, the same in both palettes: SolidFillDefault = Dark3, SolidFillHover = Dark4, SolidFillPressed = Dark5, with OnSolidFillInkDefault = Light10 for the glyph or text on them. Dark3 is the most vivid stage that still carries Light10 text at 4.5:1 in every hue (worst 5.11:1 light, 5.84:1 dark); stepping hover and pressed lighter instead fails 4.5:1 in dark. The dark palette still comes from the engine untouched, and Neutral is unchanged. A downstream theme overriding those stages must keep the IsDark delegation to the engine ramp, or it changes the dark palette too. The seed itself (Accent{Hue}) is unchanged. Surface stays off: its stages are the canvas's own tints. A downstream theme overriding a seed must repeat HueAware = true, or that hue's stages drift back to per-seed lightness.

Control themes never name a hue. They use the hue-agnostic extension, and Accent.Kind decides which hue answers:

<Setter Property="Background"  Value="{color:AccentBrush Light10}" />
<Setter Property="Foreground"  Value="{color:AccentBrush Dark9}" />
<Setter Property="BorderBrush" Value="{color:AccentBrush Light1}" />
<Style Selector="^:pointerover">
  <Setter Property="Background" Value="{color:AccentBrush Light8}" />
</Style>

One block serves a plain control, Accent.Kind="Warning" and Accent.Kind="Brand" alike. There is no .accent class — setting Accent.Kind is the opt-in, and it inherits, so a hue set on a panel reaches everything beneath it. A control that must stay neutral inside a tinted region says Accent.Kind="Neutral" explicitly.

The seed is the ink, not the fill. A hue's base value is its text and border color; fills are light stages of it. That is why AccentNeutral is #2E2E2E rather than a near-white, and why its dark seed is the reflection #D1D1D1: in the dark palette the ink is light.

Icons on the fill take the same Light10, because a PathIcon inherits its container's Foreground (Rule 13). A checked toggle that is also disabled keeps its filled face under the whole-control {size:DisabledOpacity} dim, like every other disabled control: a disabled control left at full opacity is refused by the AVLG045 gate, so the earlier "drop the fill and show DimTextDefault at full opacity" form is retired. Glyphs on a checked Dark1 fill (check marks, radio dots) are non-text: Light10 on Dark1 is 4.32:1 at worst (Error, dark), above the 3:1 they need. Do not put text on Dark1; it is 4.46:1 on the dark canvas in Error.

A surface with no border uses {color:SurfaceBorderless}. The rest fill {color:BackgroundDefault} (Light10) reads as a surface only when a border outlines it; without one it nearly vanishes into the canvas. So a borderless surface (a panel, card or host that draws no border of its own) fills with SurfaceBorderless (Light9): one stage deeper than the rest fill and one lighter than the hover fill (HoverBackgroundDefault, Light8), so it never competes with an interaction state. It follows the control's own hue like every role. A bordered surface keeps BackgroundDefault. Never copy the stage by hand: one role means changing it once changes every borderless surface. EmbeddableControlRoot is the first user.

Selected list rows are outlined, not filled. ComboBoxItem, ListBoxItem and TreeViewItem show selection the way ButtonSpinner shows state: a light fill stage of the row's own hue with {color:TextDefault} text. Selected {color:SelectedBackgroundDefault} (Light6), selected and hovered {color:SelectedBackgroundHover} (Light5), selected and pressed {color:SelectedBackgroundPressed} (Light4), no border (the row's focus uses its own inset border, Rule 21). A disabled row, selected or not, takes the whole-row {size:DisabledOpacity} like any other control. ComboBoxItem.axaml is the reference; the other two copy its selected styles. The filled column above stays for toggles.

Those two conventions are inverses and must not be mixed. A filled control that takes the outlined assignments becomes near-white text on a near-white fill — invisible, with nothing to see in a diff.

The dim role and the accent role are different colours. DimTextDefault is Dark2 and AccentInkDefault is Dark3, so a caption and an accent label are never the same colour. The stage is NOT "one step deeper" than the accent's, because the two palettes' ink ladders run in opposite directions: in the light palette the ink profile's band starts AT Dark3, so Dark3 is the lightest, most saturated ink there and Dark4 is DARKER and heavier — a dim role at Dark4 would be louder than the accent label in every hue. Dark2 is quieter than the accent ink in the dark palette in every hue and for the neutral hue in both. Measured: 15.0-27.7 RGB units apart, against 0.0 before.

Stage names are roles, not directions — Dark stages are ink, Light stages are fill. The dark palette builds each ramp as ThemeColorRamp(seed, mirror: true, stages, canvas), so Dark9 stays the readable ink and Light10 the rest fill in both. Never branch on light/dark in a control theme. A ramp that must keep the pre-1.19 dark direction (Light stages towards black) says [ColorRamp(InvertRamp = true)]; none in this theme does.

Declaring a hue is all-or-nothing. The hues carry [AccentHue], which puts the generator in explicit mode: any hue anywhere, including in a downstream theme, must then carry it too or it silently drops out of the AccentKind enum. AccentFocus deliberately lacks it — it is a role color, reached as {color:AccentFocusBrush}, not a hue a control can be. Borders use {color:BorderDefault}, which follows the control's hue.

An automatic dark counterpart is not always wanted. Mirroring gives every hue a sensible dark twin, but some seeds should simply become a different color in a dark palette rather than a mirror of themselves. ColorRamp.DarkSeed supplies that literal:

[AccentHue] [ColorRamp(DarkSeed = class="s">"#ff0000")] public virtual Color AccentSurface => Color.Parse(class="s">"#fdfdfd");

In a dark palette the whole ramp re-centres on #ff0000 — every stage, overlay and accent role derives off it, mirrored as usual — and the generator adds an effective-seed token {Hue}Seed ({color:SurfaceSeed} here): the raw seed when light, the DarkSeed value when dark. Fail-soft: a malformed hex is diagnostic ASTE035 and ignored; a valid hex with no IsDark property is ASTE037 and likewise ignored. A downstream theme overriding the seed must repeat the attribute including DarkSeed, or it loses the re-centring.

A downstream hue must supply the full stage set. AccentBrushResolver returns UnsetValue for a stage a theme does not define, so a partial hue renders with no fill and no border rather than erroring. Build it on ColorRamp like the built-in hues.

Neutral is reachable directly, and that is a different statement. {color:AccentBrush Dark1} follows whatever Accent.Kind the control carries; {color:NeutralDark1Brush} is always the neutral ramp. The Neutral* family exists for the parts of an accented control that must not take the hue — a caret, a disabled label, a divider, a scrollbar groove.

On a control with no Accent.Kind the two render identically today, which is exactly the trap: they are not interchangeable spellings. Reaching for AccentBrush where you meant neutral produces a control that silently recolors the moment it lands inside a tinted region — and Kind inherits, so that can happen far from the file you are editing. Stage properties have no markup extension. The generator suppresses them, because {color:AccentBrush Dark2} already reaches every one and ~460 entries make IntelliSense unusable. Only the base Accent{Hue} and Accent{Hue}Brush are emitted. There is no color-valued equivalent of AccentBrush, so a GradientStop or Pen can only reach a hue's base.

Shadow Theming

Shadows must change with the theme. A dark theme needs white-tinted shadows (to lift against dark surfaces), while a light theme needs black-tinted shadows. Hardcoded black shadows in a dark theme produce invisible or muddy results.

The mechanismAccentNeutralDark10 is the far end of the neutral ramp, which the mirrored dark ramp turns into a near-white lift automatically. The derived brushes apply opacity automatically:
TokenOpacityUse
{color:OverlayWeakBrush}8%Subtle depth, card shadows, hover lifts
{color:OverlayMediumBrush}16%Standard elevation, dropdown panels
{color:OverlayStrongBrush}32%High elevation, modals, focused elements
How to theme each shadow type
  • BoxShadow strings (e.g. BoxShadow="0 6 8 0 #4F000000"): Avalonia's BoxShadow is a string property and cannot be data-bound to theme tokens. Replace the BoxShadow entirely with a Border element positioned behind the target element: ``xml <!-- Shadow layer (behind the card) --> <Border Background="{color:OverlayWeakBrush}" CornerRadius="{size:RadiusMd}" Margin="0, 0, -4, -4" ClipToBounds="False"/> <!-- Main card content --> <Border Background="{color:AccentBrush Light10}" CornerRadius="{size:RadiusMd}"> ... </Border> ``
  • Gradient shadows (LinearGradientBrush, RadialGradientBrush): every GradientStop.Color takes a colour token (Color="{color:AccentNeutral}"). A stop has no Opacity, so a fade that must invert between light and dark is better drawn as a Border with {color:OverlayWeakBrush}.
  • SolidColorBrush shadow resources: use a colour token, Color="{color:AccentNeutral}", never Color="#...".

Judgement Test

When you find any hard-coded color value, apply this test before deciding whether it is exempt:

❓ "If the user swaps to a dark theme or a colorful accent theme, would this value need to change?"- Yes → This is a violation. No exemption applies. Replace with the most suitable theme token. - No → Does it fall into one of the four closed exemption categories above? If yes, it is allowed. If no, theme it anyway.

Rule

Rule 1All Control Theme Setters Must Bind to Theme Tokens

StatementEvery Setter at the ControlTheme level (i.e. direct children of the <ControlTheme> element) that sets a visual property MUST source its value from a theme token ({color:…}, {size:…} or {theme:…}) or a {StaticResource} defined within the same file. No hard-coded colors, sizes, brushes, or thicknesses at the ControlTheme level.
JustificationThis is the foundational rule. The entire purpose of the token system is that visual properties flow from a single source of truth (the theme class) into every control. A hard-coded value at the ControlTheme level defeats this: it cannot be overridden by a theme swap and must be hunted down and edited manually. By binding every setter to a theme token, we ensure that a consumer can change the theme (e.g. light → dark, or swap in a custom DefaultTheme subclass) and have the entire controls library re-style without touching individual control XAML files.
ExceptionsLogical, non-visual property values that are genuinely intrinsic to the control's behaviour (e.g. ClickMode="Release", Focusable="True", RecognizesAccessKey="True"). Also structural properties like RowDefinitions and ColumnDefinitions in templates which define layout structure, not visual style, as long as their lines are proportions or Auto: a pixel line is a size and takes a token (see the exemptions above).

Rule

Rule 2Inside a ControlTemplate, Use Only TemplateBinding

StatementWithin a <ControlTemplate>, every property that connects to the control's own styled properties MUST use {TemplateBinding Property}. Never use a theme token ({color:…}, {size:…}, {theme:…}), {StaticResource}, or hard-coded values inside a ControlTemplate.
JustificationAvalonia's style precedence means that if a value is set directly on an element inside a ControlTemplate (even via a theme markup extension), it takes higher precedence than a consumer's style that targets the same property. The consumer would then be unable to override that value through normal styling. TemplateBinding preserves the link to the control's property, which the consumer can style through the ControlTheme's setters (Rule 1) or through styles that target the control itself.
Reference exampleThe Button control uses TemplateBinding in its ControlTemplate for Background, BorderBrush, BorderThickness, CornerRadius, Content, ContentTemplate, Padding, HorizontalContentAlignment, and VerticalContentAlignment — all {TemplateBinding ...}.

Rule

Rule 3When Theme Values Are Needed Inside a ControlTemplate, Break Out to a Style on the Control's Theme

StatementIf a visual value must come from the theme but cannot be routed through a TemplateBinding (because no suitable property exists on the control, or the value needs to change based on pseudo-class state), define a <Style> that targets the inner element using the ^ /template/ ElementName selector pattern, and use the theme token there, NOT inside the ControlTemplate markup itself.
JustificationA style applied via the ControlTheme's Style children targets the visual tree from the outside and respects style precedence correctly. This means a consumer can override it with a higher-specificity style if needed. It also keeps the ControlTemplate itself "dumb" — a pure binding surface — which makes it easier to read and maintain.
Reference exampleButton's ^:pointerover and ^:pressed styles set {color:HoverBackgroundDefault} and {color:PressedBackgroundDefault}: setters on the Button's ControlTheme, not inside the template. CalendarView uses ^ /template/ styles the same way for its inner parts.

Rule

Rule 4Every Visual Property on the Control Should Be Exposed as a Setter in the ControlTheme

StatementIf a visual aspect of a control can be styled (color, thickness, corner radius, font, padding, alignment, etc.), it SHOULD have a corresponding Setter at the ControlTheme level that maps to a theme token. Do not bury visual constants inside the template or in inner styles.
JustificationThis is the corollary of Rule 2: if a property isn't surfaced as a Setter on the ControlTheme, then {TemplateBinding} has nothing to bind to, and the control becomes unstylable for that property. Exposing properties at the theme level is the contract that enables Rule 2 to work.
Carve-out — inherited properties (Rule 13).Foreground and the Font* properties inherit. For those, setting the ambient value here does not make the control stylable — it makes it unstylable from the outside, because a setter outranks inheritance. Declare them at the roots and only re-declare where the value differs. See Rule 13 before adding Foreground or Font* to the list below.

Rule

Rule 5Use the Smallest Viable Token Set — Manipulate, Don't Proliferate

StatementDo NOT add new theme tokens to DefaultTheme.cs for every control's unique requirement. Instead, compose and manipulate existing tokens (e.g. apply opacity, combine via overlays, use different shade variants) to achieve the desired appearance. Add a new token only when the same value would be genuinely useful across multiple controls and is a fundamental design dimension.
JustificationA token system that mirrors every control's idiosyncrasies becomes as complex and hard to maintain as the old system it replaces. The power of tokens comes from a small, consistent vocabulary that designers and themers can learn once. If every control needs unique tokens, the system has failed.
Patterns for manipulating existing tokens
  • Use the role stages for states (HoverBackgroundDefault, PressedBackgroundDefault, SelectedBackgroundDefault) instead of adding per-control colours.
  • Use stages ({color:AccentBrush Light6}, or the PressedBackgroundDefault role) for press-depth instead of separate press colors.
  • Use {color:OverlayWeakBrush} / OverlayMediumBrush / OverlayStrongBrush for shadows and scrims only, never as a state's Background.
  • Use {size:Scaled X} (X × BaseSize) for position/size adjustments instead of a new token; {size:Scaled {size:IconSizeMd}, X} scales another token.
  • For accent disabled opacity, use {size:DisabledOpacityAccent}, the disabled-opacity ladder's accent step (accent colors are naturally lighter so need higher disabled opacity).
  • StrokeDashArray is a specific visual choice, not a theme token — hard-code it in the template with an explaining comment.

Rule

Rule 6Font Family, Alignment, and Padding Must Be Themed, Not Hard-Coded

StatementFontFamily, HorizontalAlignment, VerticalAlignment, HorizontalContentAlignment, VerticalContentAlignment, and Padding must be set via theme tokens at the ControlTheme level, not hard-coded in the template or left as default values. The one exception is when the control's natural behaviour demands a specific alignment (e.g. a Calendar header button left-aligned for the month/year label, center-aligned for nav arrows).
JustificationThese properties fundamentally affect how a control integrates into an application's layout. If they are hard-coded inside the template, applications cannot achieve a consistent typographic and spacing rhythm across controls built from different themes. Exposing them as theme-bindable setters gives the themer full control over the app's visual harmony.

For Padding specifically, use the shared content-padding tokens rather than raw spacing steps: default content padding is {size:SpacingLg} (derived from the spacing ladder's default step), and button-like faces (Button, RepeatButton, ToggleButton, SplitButton, DropDownButton, HyperlinkButton) step their horizontal edges up with {size:SpacingXl}, leaving vertical edges on {size:SpacingLg}. HyperlinkButton takes Button's padding too.

Rule 7Named Sub-Themes for Internal Controls Use {StaticResource} Lookup

Rule

Rule 13Inherited Properties Are Declared Once at the Root and Only Re-Declared Where They Differ

StatementForeground, FontFamily, FontSize, FontWeight, FontStyle and FlowDirection are inherited properties — a value set on a control flows down to every descendant automatically. The theme establishes these once, at the roots (Window, PopupRoot, EmbeddableControlRoot, OverlayPopupHost, and LightDarkPreview, which is the root of a design preview because a preview has no themed window above it). ThemeVariantScope is not a root: this theme has no theme for it. A ControlTheme should then set an inherited property only when its value differs from what the control would inherit. If the value would be the same, leave it unset and let it flow.

This is the one deliberate carve-out from Rule 4. Rule 4 exists so nothing is hard-coded and everything is themeable; for inherited properties that goal is already met at the root, and re-declaring the same value at every control actively breaks the theme.

JustificationInheritance is the lowest priority band in Avalonia (Inherited = 4). Any value that is actually set — a plain ControlTheme setter at Style (3), a {TemplateBinding} at Template (2), a pseudo-class style at StyleTrigger (1) — beats it. So a setter does not merely "state the default": it permanently pins the property, and every ancestor's value, including that ancestor's state and class styles, is blocked from ever reaching the control. The property becomes unreachable from the outside.

Concretely: a control that pins Foreground cannot participate in an accent container, a selected row, a hover state, or a disabled parent, because none of those values can reach it. The container's state style fires, the container's own foreground changes, and the pinned descendant stays exactly as it was.

Reference violation (the case that produced this rule)PathIcon set Foreground to {color:AccentBrush Dark1} in its visual defaults. Every icon in the library was therefore nailed to the neutral color. When ButtonSpinner set Foreground to {color:AccentPrimaryDark1Brush} on its spinner buttons for hover, the chevron glyph did not change — the icon's own setter (priority 3) outranked the inherited value (priority 4). The fix was to delete the setter, not to add a louder override in ButtonSpinner. One deletion made every PathIcon in the library accent-aware, state-aware and dark-variant-aware at once, because they all now resolve through their container.

Note the shape of the trap: the wrong fix (push the color down from each container that needs it) appears to work for the control in front of you and has to be repeated forever. The right fix (stop blocking inheritance) is a deletion.

Rule 14Theme Exception: Marks a Deliberate Deviation — Never "Fix" What It Guards

StatementA comment whose text begins with exactly Theme Exception: marks the line below it as a known, reviewed deviation from a rule in this document. Do not change that value, do not replace it with a theme token, do not delete the marker. This overrides every other rule here.

The marker must state why in the same comment. A bare Theme Exception: with no reason is not a valid exception — it is a hard-coded value wearing a label, and should be challenged.

<!-- Theme Exception: Stretch required to make spinner button hover effects full height -->
<Setter Property="VerticalAlignment" Value="Stretch" />
JustificationMost rules here are pattern-matchable — "an alignment setter with a bare string is a violation" (Rule 12), "a Foreground setter restating the ambient value is a violation" (Rule 13). That is exactly what makes them enforceable, and exactly what makes them dangerous: a reader or an agent sweeping the library will find a legitimate deviation, recognise the pattern, and "correct" it. The value looks wrong in isolation and is right in context. Without a marker the reason lives only in whoever's head wrote it, and the fix gets silently undone — usually with a green build, because these are visual regressions.

The marker converts an invisible intention into a checkable fact. It also makes the deviations auditable: grep -rn "Theme Exception" Controls/ lists every place the theme knowingly departs from its own rules, which is a far more useful review artefact than a clean-looking file that quietly disagrees with the docs.

Scopea marker guards the single setter or element immediately below it. To cover a block, either mark each line or say so explicitly in the comment (Theme Exception: ... — applies to all four setters in this style).
If you believe an exception is wrongsay so, don't edit it. Raise it with the reason you disagree. The marker means someone hit a real problem and chose this deliberately; the burden is on the challenger to show the original reason no longer holds.
When writing a new oneexhaust the themed route first. An exception is for values that are structural or intrinsic to the control's mechanics — a full-height hit area, a positional class like TopLeft, an indeterminate progress bar's travel — not for "the token didn't look quite right", which is a request to change the token.
Tooling notenothing checks the alignment-token or inherited-property rules automatically today; the marker binds readers. Any check added for them later must skip a setter preceded by a Theme Exception: comment, or it will produce exactly the false positives this rule exists to prevent.

Rule 18Controls Draw Like the Web — Clip Only Where a Part Is a Viewport

StatementWebRenderStyle in DefaultTheme (on by default) makes the theme draw the way a browser does. Two tokens carry it, and a control theme uses the tokens, never the toggle:
TokenOnOffUsed by
{theme:ControlClipToBounds} (bool)falsetruea ClipToBounds setter in the visual defaults of every ControlTheme whose target is a TemplatedControl
{size:HoverZIndex} (int)10any state that grows a control, beside its RenderTransform (Button's ^:pointerover)

A subclass turns it off with public override bool WebRenderStyle => false;, and Avalonia's defaults come back: every templated control clips to its own bounds and nothing is lifted.

It is a setter like every other theme value, so it can be overridden the same way. Every ControlTheme for a TemplatedControl carries <Setter Property="ClipToBounds" Value="{theme:ControlClipToBounds}" /> with its other visual defaults. A consumer's own ControlTheme (BasedOn this one or not), a Style, or a local value all beat it, exactly as they beat the theme's Background. A new ControlTheme for a templated control adds the setter too. A theme BasedOn another inherits it and doesn't repeat it. ContentControl gets its template from code (ContentControl.cs:48), so it has a ControlTheme here that carries only this setter.

Pages: one narrow Style. A ControlTheme is found by exact type (StyleKey defaults to GetType(), StyledElement.cs:299,667), so no theme reaches an app's pages: every page is its own MyPage : UserControl subclass. Theme/DefaultThemeStyles.axaml therefore adds one Style, :is(UserControl), carrying the same token, and every page follows the toggle. A page's local ClipToBounds, or a consumer Style nearer the page, still beats it.

A custom templated control with no theme of its own keeps Avalonia's clip. No theme setter or page style reaches it, and that is accepted: such a control needs its own ControlTheme anyway, and that theme carries the setter like every other.

Deliberate exceptionsPipsPager's item theme sets ClipToBounds="False", because its pips draw past their slots in both states. TransitioningContentControl clips its template's root panel locally, because its slide must stay inside it.
WhyAvalonia clips every TemplatedControl to its own bounds (TemplatedControl.cs:130), so a page, a card or any ContentControl cuts a hover grow at its edge. The web's default is overflow: visible; only a box that asks to clip does. Paint order is the other half: a later sibling paints over an earlier one, and ZIndex reorders siblings of one parent only, so a grown control needs ZIndex to paint over the neighbour it overlaps.
Where the clip stays
  • Scroll viewports. ScrollContentPresenter is not a TemplatedControl and clips by itself, so scrolled content never draws over a header. A grow at the very edge of a viewport is still cut there, as on the web.
  • A template part that is a viewport says so with a local ClipToBounds="True", which no setter or style can remove: TransitioningContentControl's root panel (its slide would otherwise draw over its neighbours), TextBox, SplitView, NavigationPage, TabControl, ProgressBar, DropDownButton, CommandBar, CalendarView and NotificationCard.
What follows from it
  • Content larger than its control is no longer cropped and will show over its neighbours. Clip that one place on purpose; never add margin to "make room".
  • Hit-testing follows the drawn pixels: a grown control takes the pointer over the area it covers. Keep grows modest.
  • A floating element that must escape every container goes on the AdornerLayer with IsClipEnabled="False", or in a Popup.

Measured (Avalonia 12.0.1): a hovered Button in the top-left corner of a page UserControl is drawn on all four sides with the toggle on and cut by the page (left 4.84px, top 0.85px) with it off; its bottom edge paints over the next button only while HoverZIndex is 1; a scroll viewport still masks scrolled-off rows; and a TransitioningContentControl PageSlide stays inside its bounds at 75, 150 and 225ms.

Rule 19Nothing Inside a Rounded Frame Paints Past Its Curve — Parts Follow It, Frames Don't Clip

StatementA part that paints (a fill, a stroke, a ring) and touches a rounded frame's corner takes a radius concentric with the frame, from {size:ConcentricCorners}, on exactly the corners it touches. A rounded frame never relies on ClipToBounds to hide what its children paint.
Why (Avalonia 12.0.1)a Border's CornerRadius is the middle of its stroke ("the corner radius is defined to be the middle of the stroke", GeometryBuilder.cs; BorderRenderHelper strokes the rect deflated by t/2 with the full radius). So the stroke's drawn outer edge is radius r + t/2 at the bounds and its inner edge, where children are arranged, is r − t/2 at inset t. A square child, or one given the frame's own r, paints over the stroke at every corner. ClipToBounds on a Border clips to RoundedRect(bounds, r) (BorderVisual.cs): the outer box at r, which is tighter than the frame's own stroke (it shaves its outer anti-aliasing) and still lets a child cover the stroke. The web clips overflow: hidden children to the padding box at the inner radius; Avalonia has no such clip, so the part carries the shape itself.
The helperfor a part whose bounds sit d inside the frame's bounds and which strokes its own outline T wide, ConcentricCorners returns r + t/2 − d − T/2 per selected corner (0 where the frame is square). Inset defaults to the frame's Thickness, the common case of a child inside the frame (giving r − t/2). A part at the frame's own bounds passes Inset = its Margin (0), and a ring outside passes its negative Margin. It reads TemplateBindings, so a restyled CornerRadius or BorderThickness is followed.
Where it is used
  • ButtonSpinner: the value presenter and the outer spinner button take the inner curve on the side they touch (both sides swap under :left; all four corners when ShowButtonSpinner is false). This replaces the old {size:Corners} workaround, which gave the button the frame's own r.
  • Focus ring (AdornerLayer.axaml): the default focus adorner is outset around the control by its own width plus the halo's, and both of its rings are concentric with the focused control. They read the control through AdornerLayer.AdornedElement, which Avalonia sets to the focus target (Control.cs OnGotFocus). It was a square ring drawn inside the control's bounds.
  • ToggleSwitch: the checked track covers the outline exactly, so it takes the outline's drawn outer edge (inset 0).
  • A fill that should sit inside a sibling frame uses Avalonia's own inner-edge geometry, BackgroundSizing="InnerBorderEdge" (ComboBox's focus highlight).
  • A field inside another control's frame uses the DefaultFramelessTextBox sub-theme from TextBox.axaml (Rule 7; no border, no fill in any state): the editable ComboBox and the CalendarView picker. It replaces CalendarView's private DefaultCalendarViewTextBox, which covered focus and disabled but not hover.
  • Items inside a popup or list container (ComboBoxItem in the drop-down, MenuItem in ContextMenu, MenuFlyoutPresenter and every submenu) are concentric with the container even though they don't touch its corners: the item radius is the container's radius minus its padding and border, ConcentricCorners with Inset = the container's padding plus thickness, so the item's curve runs parallel to the container's.
  • A part that doesn't need its own fill has none (TreeView's scroller), and a frame that must mask content clips on an inner panel, not on itself (DropDownButton).

Measured with a supersampled corner check against Avalonia's stroke geometry, every crawler state, light and dark, at scale 1 and 2. OUT is pixels past the outer arc and RING is pixels of the stroke painted over; the second figure is scale 2. Rule

Rule 21The Focus Ring Is Magenta Only on Neutral Controls — Accented Controls Keep Their Own Hue

Focus never changes a control's size. The focus state sets the border's weight to the control's RESTING weight, so a focused control's border box keeps exactly its rest size (thickening it to ThicknessMd grew auto-sized controls by 2px, shifted layout and broke the state-pass restore, AVLG030). The focus weight is carried by the default focus adorner (AdornerLayer.axaml): a 2px {color:AccentFocusBrush} ring with a thin light halo, drawn concentrically OUTSIDE the control (Rule 19), so it consumes no layout. The control's own border still takes the focus colour below. A control must not null its FocusAdorner unless it draws an equivalent outset ring itself. A pinned Preview.State="Focused" example shows only the focus-colour border, because the outset ring belongs to real keyboard focus.

StatementA focused control announces itself at its RESTING border weight in a colour decided by the theme's FocusColorOnAccents switch (default false) and the control's effective hue:
TargetSwitch off (default)Switch on
Neutral (no chromatic hue above it){color:AccentFocusBrush} (magenta){color:AccentFocusBrush} (magenta)
Non-neutral (Warning, Success, …)its own hue at the focus-border stage{color:AccentFocusBrush} (magenta)

So with the default, a Warn or Success control that gains keyboard focus keeps its own amber/green border, in a darker stage at the same weight (Dark1, the accent's own hairline stage, against the Light1 rest border), instead of turning magenta; only neutral controls borrow the dedicated focus colour. Setting FocusColorOnAccents to true makes every focused control magenta.

The mechanism — use the tokens, never the toggle. A control theme writes the focus state exactly as it always did, but pointed at the theme's own role token:

<!-- Focus state -->
<Style Selector="^:focus-visible, ^[(theme|Preview.State)=Focused]">
  <Setter Property="BorderBrush" Value="{color:AccentFocusBorder}" />
  <Setter Property="BorderThickness" Value="{size:ThicknessSm}" />
</Style>

(xmlns:color="using:AngelSix.ThemeEngine.Colors" is already on every control file.) {color:AccentFocusBorder} resolves, against the element that receives the setter, to AccentFocusBrush when the target is neutral or the switch is on, and to the target's own Accent{Hue}{Stage}Brush otherwise — where {Stage} is the value of the AccentFocusBorder role read off the resolved theme instance at render time (currently Dark1, so AccentWarningDark1Brush), never hard-coded. Both the switch and the stage are read off the resolved theme instance (honouring a scoped region, exactly like the engine's own converters), so every focused accented control changes at once from one value:

theme.FocusColorOnAccents = true;   class="c">// every focused control magenta
class="c">// or, in the theme's own class, move the role's stage:
[AccentRole(NeutralHue = class="s">"Neutral", FocusColour = nameof(AccentFocus), FocusSwitch = nameof(FocusColorOnAccents))]
internal virtual RampStage AccentFocusBorder => RampStage.Dark5;

Do not branch on the hue yourself in a control file, and do not special-case the focus colour per accent — that is what this rule centralises. The decision is DECLARED, not computed: the AccentFocusBorder role carries the engine's FOCUS HUE SWITCH policy (NeutralHue = "Neutral", FocusColour = nameof(AccentFocus), FocusSwitch = nameof(FocusColorOnAccents)), and the engine resolves it per hue, inside its own reactive binding — so a change of Accent.Kind re-resolves the focus colour with no other trigger. The C# helper (Theme/FocusBrush.cs, now deleted) resolved the hue once through a Self binding, which is why a focused control kept the old accent's focus colour until it was clicked. The stage lives in DefaultTheme.AccentFocusBorder. To change the accented-focus stage, move AccentFocusBorder; to change the policy, flip FocusColorOnAccents. Moving the role measurably moves the ring: with AccentFocusBorder = Dark5 a focused Warning box draws #FF3F2D00 light / #FFDEB65E dark instead of #FF9C5F00 / #FFC37800, while a focused neutral box stays #FFBF4AF9 in both panes.

Why a converter and not a selectorthe choice depends on two things at once — the theme boolean and the control's inherited theme:Accent.Kind — and the latter does not reliably reach a template part as an inheritable value in this host. FocusBrush therefore resolves the OWNING CONTROL first (a template part walks TemplatedParent up to the outermost templated control the focus style attaches to) and then climbs the visual ancestry from there, stopping at the first element whose effective hue is set — which is also how the engine's own {color:AccentBrush} behaves. Measured agreement: a focused Warning box's border equals the engine-native {color:AccentBrush Dark1} on a sibling in the same pane, light and dark (light #FF9C5F00, dark #FFC37800); a focused neutral box is #FFBF4AF9 (AccentFocus) in both panes.

Known limits. Two behaviours are measured, not assumed:

  1. Liveness: the binding re-evaluates each time the focus state applies, so a hue change while a control stays focused shows on the next focus.
  2. Explicit Neutral inside a tinted region: the engine erases an explicit Accent.Kind="Neutral" assigned on an element inside a coloured region — assigning the default stores no local value, so at runtime GetHue reports the REGION'S hue and IsSet(HueProperty) is false (measured: a focused box pinned Neutral inside a Warning StackPanel reads Name=="Warning", IsSet==false; the identical box at top level reads Name=="Neutral"). A deliberately-neutral control inside a tinted region therefore takes the region's hue for its focus border until the engine preserves such assignments; the escape hatch is to wrap the control in its own untinted container.
Accessibility floora focused accented control must still differ visibly from its resting state — hence the darker Dark1 border, never a focus state identical to rest.

Rule 22Each Size Ladder Moves Only What It Names

StatementHit targets and control faces (buttons, pip cells, strips, grips, splitters) take ControlHeight steps. Glyphs (icons, dots, chevrons) take IconSize steps. Gaps (padding, margins, spacing, the band round a modal) take Spacing steps. Content widths (columns, panes, rails, a split view's width) take BaseSize or ControlMinWidth, never Spacing or ControlHeight.
Whya value on the wrong ladder vanishes when an unrelated setting goes to 0: dots sized by spacing disappear at spacing 0, columns sized by spacing collapse, a page header sized by control height disappears.

Rule

Rule 23A Control-Height Value On Something That Holds Content Is A Floor

Statementan element holding text or an icon takes MinWidth/MinHeight from a ControlHeight token, never a fixed Width/Height. Fixed sizes stay only on bare faces with no content, and on rows a scroller snaps on. A template ContentPresenter binds HorizontalContentAlignment/VerticalContentAlignment so its content centres, and a control with a hover state paints a background (Transparent if nothing else) so its whole face catches the pointer (AVL035).
Whya fixed size crops its content when the ladder shrinks and lets padding push the content sideways; an unpainted face is hit only over its text, so a growing hover flickers.
